# internal/api/handler/** 里自己路由自己的函数(包.接收者.函数名,⛔ 不含行号)。
#
# 一条 mux pattern 注册进去,handler 在函数体里用 TrimPrefix/HasSuffix/SplitN
# 把 r.URL.Path 再切成好几个逻辑端点。初始基线里最极端的三个是
# settings.go 18 个端点、rule.go 12 个、wallet.go 8 个 —— ⭐ 三个都已经拆掉了
# (提案 S5 / S8 / S3),这份清单现在剩下的每一行都比它们小。
#
# ⛔ 这就是 OpenAPI 注解写不下去的原因:一个还在切 URL.Path 的函数,
# 它的 @Router / @Summary 只能是猜的 —— 没有唯一的 path,也没有唯一的 method。
# 所以拆解必须在 spec 之前,而这道门禁盯的是 **handler 一侧**。
#
# ⭐ 为什么必须盯 handler 而不是注册侧:router.go:437,445,446 已经用
# {address} 通配符注册了,而 `grep -rn "PathValue" internal/` 全仓 **0 次** ——
# 通配符是装饰性的,handler 照样手工切。按注册侧计数的门禁今天就会显示
# 「修了一部分」,而通配符背后一个字都没变。
#
# 每修好一个 handler(按子路径注册 + 改读 r.PathValue),这里少一行;
# 退回去则棘轮反向报红。⛔ 别往里加行 —— 基线里的每一行都是一个
# 生成不出 SDK、也写不出诚实注解的端点组。
#
# 初始规模(2026-09-10,由 `go run ./cmd/archcheck -list handler-path-dispatch`
# 生成,⛔ 不是从棘轮 diff 手抄的):**20 个函数,17 个文件**。
# 草案 docs/drafts/openapi-chain-proposal.md §5 估的是「16 个文件、20–26 条」——
# 条数落在下沿,文件数多 1(草案漏算了 approval.go 里的第二个 handler:
# ApprovalHandler 和 PreviewRuleHandler 各有一个 ServeHTTP)。
#
# ⚠️ 其中三条不是路径分发,只是把 path 写进日志(evm.SignHandler.ServeHTTP、
# evm.ApprovalHandler.ServeHTTP 与 evm.PreviewRuleHandler.ServeHTTP 的
# logger.Warn("...", "path", r.URL.Path))。判据没有为它们开口子:要区分
# 「只是记日志」和「在分发」,得猜调用上下文,而先赋值给局部变量就能骗过去 ——
# 松判据比没判据更糟。⭐ 拆解到它们时顺手把日志改成 r.Pattern 或结构化字段,
# 这几行同样会消失。
#
# ⚠️ evm.RPCProxyHandler.ServeHTTP 留在基线里,没有豁免。草案 §2.6 说
# rpc_proxy「不安全触碰」—— 那是拆解 PR 的排期判断,不是判据的例外:
# 它的 TrimPrefix(r.URL.Path, "/api/v1/evm/rpc/") 取 chainID,正是 PathValue
# 该接手的那种读法。豁免它等于用排期理由藏掉一条可修的。
#
# ⛔ 不在范围内(判据按包前缀切,理由写在 cmd/archcheck/pathdispatch.go):
#   - internal/api/middleware/ —— auth.go:97-100 必须对**客户端签过的原始字节**
#     签名(preset id 含 '/',JS SDK 送 %2F,PathValue 给的是解码后的段,
#     "修好"它等于把这类请求一律 401);其余全是审计日志里的请求行。
#   - internal/api/router.go 的 SPA 兜底、internal/web/handler.go 的静态文件。
#

#（提案 §0 订正 5)与「基线里有几条」不是一回事 —— 这道判据数的是**读 path 的

# ⭐ 这正是后面 S4–S8 估工作量时最容易估错的地方:基线少一行 ≠ 少一个端点。
# 那 8 个端点现在是 internal/api/module_wallets.go 里 8 条 method+wildcard

# 2026-09-10 · 提案 S4（hd-wallets 拆解):**19 → 18 条,16 → 15 个文件**。
# 删掉的是 `internal/api/handler/evm.HDWalletHandler.ServeHTTP` —— 一条,
# 背后是 4 个端点(list / create-import / derive / derived)。
# ⚠️ 注册侧是 **4 条 pattern → 4 条 pattern**,数字一动不动,而其中两条原本是
# 通配前缀(`/api/v1/evm/hd-wallets` 不限方法、`/api/v1/evm/hd-wallets/` 任意深度),
# 另两条虽然写着 `{address}` 却从没被读过 —— handler 照样 TrimPrefix/SplitN 自己切。
# ⭐ 也就是说「按注册侧数」在这一步会显示**零进展**,而实际上一个吞掉整棵子树的
# 前缀消失了,`{address}` 第一次真的经 PathValue 送到 handler。这正是本判据
# 盯 handler 侧而不是注册侧的理由,在 S4 上比在 S3 上更明显。

# 2026-09-10 · 提案 S4(signers 拆解,S4 的最后三分之一):**17 → 16 条**,文件数不变(14)。
# 删掉的是 `internal/api/handler/evm.SignerHandler.HandleSignerAction` —— 一条,
# 背后是 **9 个端点**(item DELETE/PATCH、unlock/lock/approve/transfer、
# access 的 list/grant/revoke),外加 `ServeHTTP` 的两个(list/create)。
# ⚠️ `SignerHandler.ServeHTTP` 和 wallet 那次一样**从来不在基线里** —— 它只
# `switch r.Method`。所以这一步基线只少一行,而注册侧 **7 条 pattern → 11 条**。
# ⚠️ 文件数**没动**:`HandleWalletSigners` 从 signer.go 挪到了 signer_wallet.go
# (见下),一个文件退出、另一个文件进来。key 是 `<pkg>.<Recv>.<FuncName>`,
# 不含文件名,所以这次挪动对基线本身是不可见的 —— 这里写出来是免得下一个人
# 拿文件数去核对条数。
#
# ⛔ 这一步和前两步不同,它关的是一个**已经发生过**的洞:
# `/api/v1/evm/signers/` 注册时不带 method,于是它匹配所有动词,而 Go 的 mux
# 只有在「路径匹配、方法都不匹配」时才回 405 —— 有这个前缀在,永远有一条匹配,
# 405 永远不会发生。`GET .../{address}/unlock` 因此真的解锁了 signer,
# `DELETE .../{address}/approve` 真的批准了(6d30ba1)。那次修的是 handler 里
# 加一道显式 method 守卫;这一步把守卫删了,因为**没有 pattern 再把这些动词
# 路由到任何地方** —— 这是两种不同的东西:一条要有人记得写的规则,和一条
# router 忘不掉的规则。
#
# ⛔ `SignerHandler.HandleWalletSigners` 留在基线里,而且它是**没有任何路由
# 注册的**:全仓找不到 `/api/v1/evm/wallets/` 这条 pattern,pkg/client、web/src、
# e2e/ 也没人请求它,它只被自己的 6 个测试调到。删一个带测试的导出方法不是
# 「给每个端点一条路由」这件事的执行细节,所以这次不删 —— 它是一个决定,
# 该单独判断(见 signer_wallet.go 上的注释)。

# ⭐ 2026-09-11,提案 S5:**16 → 15**,删掉的是
# `internal/api/handler.SettingsHandler.ServeHTTP` —— 一条,背后是 **18 个端点**
# (9 个 group × GET/PUT),是这张表里单条含端点数最多的一行(rule.go 的 12 条
# 现在排第二)。
#
# ⛔ 这一条和前三步关的洞不一样,值得写清楚:settings 没有动词洞,也没有吞路径。
# ServeHTTP 是 `switch r.Method` + 405 default,GET 改不了任何东西(实测:拿四个
# 动词各打一次真 manager,读回快照,只有 PUT 变);`strings.Contains(group,"/")`
# 把每一条深路径挡在 400,没有 signers 那种 `.../access/a/b` 返回真实列表的事。
# 它关的是**另一个洞**:请求体的类型随路径里的一段变 —— 9 个 group、9 种互不相干
# 的 body 结构、一条 path。OpenAPI 一条 path+method 只有一个 requestBody schema,
# 所以这条 pattern 在 spec 里唯一诚实的写法是「什么都不写」。
# ⛔ 修法必须是**每个 group 一条字面量路由**:`PUT .../{group}` 通配符会把类型
# 选择从 handler 挪到路由表,而 body 类型仍然随 path 的**取值**变 —— 路由表看着
# 拆开了,表达不了的形状原封不动。

# ⭐ 2026-09-11,提案 S6:**15 → 13**,删掉的是
# `internal/api/handler.PresetHandler.ServeHTTP` 与
# `internal/api/handler.TemplateHandler.ServeInstanceHTTP`。
#
# 前者背后是 **4 个端点**(list / detail / apply / validate),它切的是
# `r.URL.EscapedPath()` 而不是 `Path` —— preset id 是文件名词干、含 '/',客户端
# 送 %2F,所以它必须在编码态上切、再 `url.PathUnescape` 还原。⭐ 现在这一整套
# 没了:Go 的 mux 按段拆**编码后的**路径、再逐段解码,`{id}` 直接就是
# "evm/weth"。⛔ 这也是这条判据把 middleware/auth.go 排除在外的那条理由的**另一
# 面**:签名必须对客户端签过的原始字节,而路由**恰恰**应该读解码后的段 ——
# 两者读的是同一个 URL 的两种形态,谁也代替不了谁。
#
# ⛔ 后者关的是一个**真的洞**,和 6d30ba1 一模一样:`GET /api/v1/presets/` 不带
# 子路径限制地匹配整棵子树,而 ServeHTTP 的三个分支都写着注释「不用判 method,
# GET 和 POST 是分开注册的,mux 已经挡掉别的了」—— 那句话是错的,子动作根本不在
# pattern 里。实测(0866784,带 JS evaluator 的真 handler):
#   GET /api/v1/presets/evm%2Fgp/apply  + JSON body  → **201 Created,写了一条
#   rule 实例**,全程只拿着 read_presets,apply_preset 一次都没被问到。
#
# ⚠️ TemplateHandler.ServeInstanceHTTP 背后只有 1 个端点,但它是
# **setupRoutes 里那个 inline 闭包**的另一半(闭包按 `HasPrefix(path,
# "/api/v1/templates/instances/")` 分发)—— 一张藏在路由表里的第二张路由表,
# 任何读注册的门禁都看不见它。
#
# ⛔ `internal/api/handler.TemplateHandler.ServeHTTP` **留在基线里**,而且这一步
# 拆不掉:template id 同样是含 '/' 的文件名词干,但 pkg/js-client、extension、
# web/src 和两个 e2e 用例都是**不编码**直接拼进路径的(pkg/client 与 pkg/rs-client
# 编码)。未编码的 '/' 让 `/api/v1/templates/a/b` 同时是「模板 a/b」和「模板 a 的
# 子动作 b」,只有一张已知后缀表能分开它们 —— 那正是 ServeHTTP 里那串 TrimSuffix。
# 换句话说:这几个端点**在客户端改口之前不可命名**。三条出路写在
# internal/api/module_templates.go 上,⛔ 那是一个决定,不是重构的执行细节。

# ⭐ 2026-09-11,提案 S7(requests 闭包拆解):**12 → 8 条**,删掉四条:
# `evm.RequestHandler.ServeHTTP`、`evm.ApprovalHandler.ServeHTTP`、
# `evm.PreviewRuleHandler.ServeHTTP`、`evm.RequestSimulationHandler.ServeHTTP`。
# 注册侧是 **3 条 pattern(其中两条不带 method)→ 6 条具名路由**。
#
# ⚠️ 这一步和 templates 那次一样,四条里有两条**不只是**在分发,它们还把
# `r.URL.Path` 写进了 json 解码失败的 warn 日志(基线开头那段「三条只是记日志」
# 说的就是其中两条)。判据不为记日志开口子,所以那两行同样得改 —— 改成
# `"pattern", r.Pattern`,它说的是同一件事而且更准:请求匹配的是哪条路由。
#
# ⛔ 这一步关掉的洞与 signers(6d30ba1)、presets 的形状不同,值得写清楚:
# 四个分支**都**检查了自己的 method(拿 ProcessApproval / PreviewRuleForRequest
# 的 spy 实测过:每一个错动词都回 405 且一个服务调用都没发生),所以没有
# 「GET 能改状态」那种事。真正的洞是**吞路径**:闭包按 `HasSuffix(path,"/approve")`
# 挑分支,handler 把 id 读成 `parts[len-2]`,于是前面有几段都收、且一律忽略 ——
# 实测 `POST /api/v1/evm/requests/a/b/approve` **回 200 并批准了 request "b"**,
# `.../a/b/c/d/approve` 批准了 "d"。⛔ 一个会改状态的端点,路径上写的 id 和真正被
# 改的那一行不是同一个 —— 审计日志记下的路径因此是误导的。
# 这不是越权(approve_request 照样要有),是 id/路径混淆。`{id}` 只吃一段,
# 所以那些形状现在匹配不到任何 pattern。

# ⭐ 2026-09-11,提案 S8(rule.go 拆解,分三刀):**8 → 7 条**,文件数 8 → 7。
# 删掉的是 `internal/api/handler/evm.RuleHandler.ServeHTTP` —— 一条,
# 背后是 **12 个端点**,是这张表里单条含端点数第二多的一行(仅次于 settings 的 18)。

# !strings.Contains(ruleID, "/")`。别的 handler 没有这道守卫,所以别的 handler 有洞。

# ⛔ 真正的洞在**尾斜杠**,而且在两个会改状态的端点上:ServeHTTP 先
# TrimPrefix 掉 "/api/v1/evm/rules" 再 TrimPrefix 掉开头的 "/",于是空余量 = **集合**,

# Go 的 mux 不剥尾斜杠,所以这两个形状现在匹配不到任何 pattern。

# ⚠️ 这一步有几道守卫必须**逐条搬**,它们住在 ServeHTTP 里而不在端点函数里:

# 两条 budget 分支的 `len(id) <= 128`(⛔ {id} 只限一段,不限长度)。
